# 事故定责 Skill

## 触发条件

用户询问“谁的责任”“是否有责”“责任团队怎么判”“定责比例/有责事故数怎么算”，或要求依据事故材料生成定责分析时触发。定责必须在事故事实、时间线和影响范围基本可核验后进行；如果用户只有现象描述，先补齐输入，不直接归责。

## 目标与边界

- 依据《线上事故定责原则》和《定责流程》逐条比对事实，输出可复核的责任分析。
- 责任对象是具体团队/责任域，不把受影响业务方直接当作责任团队；二者必须分开记录。
- 定责结论是智能体辅助分析，供评审参考，最终以正式定责组织裁定为准。
- 不因“最后处理事故的团队”或“发现问题的团队”自动认定责任；责任需有违规事实、因果关系和证据支撑。

## 必填输入

| 信息 | 要求 |
|---|---|
| 事故标识 | 事故名称或事故 ID，保证材料可追溯 |
| 受影响业务方 | 业务方名称；用于影响面，不等同责任团队 |
| 事故发生时间 | 带日期、分钟和时区；默认 `Asia/Shanghai` |
| 完整时间线 | 发生、发现、定位、止损开始、完全恢复、验证恢复 |
| 故障现象与影响 | 受影响功能/指标、用户/订单/资损范围、持续时间 |
| 初步原因 | 直接原因、触发条件和已知放大因素；未知写“待定位” |
| 涉及团队/系统 | 变更方、开发方、值班方、业务方、依赖方等候选 |
| 证据 | 变更记录、发布单、监控、日志、评审、测试、预案、沟通记录链接或原文 |

已定级结果、责任相关制度条款、是否存在预案/监控/测试/变更缺口为优先补充项。缺少关键事实时，先输出待补充清单，不猜测责任团队。

## 关键口径

1. **责任事实与原因事实分离**：根因可能是配置、代码、流程或依赖问题；责任判断还需确认团队是否拥有控制权、是否违反已发布规范、是否有合理预防机会。
2. **故障时长口径一致**：业务受损（核心指标开始下降）至业务开始恢复上涨；完全恢复时间单独记录，不擅自替换故障时长。
3. **中后台不可用时长、L0S 扣除、有责事故数**：仅在对应制度适用且输入齐全时计算，展示公式、单位、时间范围和四舍五入规则；不以估算值代替制度数据。
4. **共同责任**：只有每个团队的事实、控制边界和因果贡献均能独立证明时，才列为共同责任；无法区分贡献度时输出“责任待评审”，不擅自分配比例。

## 执行流程

1. 读取定责原则和流程正文，提取适用条款、责任分类、评审节点和需要的证据。
2. 建立事实表，标注来源：用户提供、系统/监控取数、文档原文、智能体推断、待人工确认。
3. 规范时间线和时区，核对发生/发现/止损/恢复端点与定级结果是否一致；冲突列为待确认。
4. 按候选团队逐一检查：是否拥有相关系统/配置控制权、是否实施或审批变更、是否有测试/评审/监控/预案职责、是否违反明确要求、是否存在可合理避免的机会。
5. 对每条候选责任给出“事实 → 条款 → 因果链 → 证据 → 反证/不确定性”，区分主责、次责、无责和待评审。
6. 如需计算影响或扣除，列出公式、代入值、数据来源、时间区间和缺失字段；计算结果与定级/通报口径交叉核验。
7. 输出责任分析、待评审问题和下一步取证动作；不替评审组织发布最终裁定。

## 输出模板

```markdown
## 责任结论（供评审参考）
**结论：** <主责/次责/无责/责任待评审；若证据不足明确写待评审>
**责任团队：** <团队或“待确认”>
**责任类型：** <变更、代码、配置、流程、监控、预案、依赖等>
**置信度：** <高/中/低>
**说明：** 智能体分析结果，最终以正式定责评审为准。

## 事实与条款比对
| 候选团队 | 已确认事实 | 适用条款/要求 | 因果关系 | 证据 | 结论 | 不确定性 |
|---|---|---|---|---|---|---|

## 影响与计算（如适用）
- 故障时长：<起止端点、分钟数、来源>
- 影响指标/用户/订单/资损：<数值、基线、时间范围、来源>
- 扣除或其他制度计算：<公式、代入值、结果；无数据则写待补充>

## 待确认与下一步
- <需要谁提供什么证据、截止时间、评审节点>
```

## 异常处理

- 团队名称、责任边界或用户提供的中文姓名无法唯一映射时，列出候选并询问，不发送或通知任何人。
- 仅有业务方、事故时间而没有原因和证据时，可先返回“待定责”及取证清单，但不得输出确定责任。
- 文档、监控或日志无权限/不存在时保留原链接和错误信息，标记“未核验”，不得用搜索摘要冒充正文。
- 发现定级、通报、复盘之间的时间或影响口径不一致时，先指出冲突，再分别保留来源，不静默覆盖。
