# 事故通报 Skill

## 触发条件

用户要求“发事故通报”“通报一下事故”“同步事故进展”“生成管理层简报”，或需要针对 P0/P1 事故组织内外沟通时触发。本 skill 只生成通报草稿和升级提醒，不直接向群聊、客户、管理层或外部机构发送消息。

## 目标与边界

- 在事实可追溯的前提下，先给出事故当前状态，再给出影响、处置和下一步。
- 区分内部事故群、管理层、业务方、客服/运营、舆情/G 侧等对象，按对象控制信息范围。
- 只使用已确认数据；未知信息用“待确认/待补充”占位，不用估算值补齐。
- 通报是沟通产物，不替代事故定级、定责和正式发布审批；等级未确认时明确标注“暂定/待定”。

## 必填输入

| 信息 | 要求 |
|---|---|
| 事故名称/ID | 可追溯的事故标识 |
| 受影响业务方 | 业务方名称及受影响功能；不要写成责任团队 |
| 事故发生时间 | 带日期和分钟，默认 `Asia/Shanghai`；与事故定级口径一致 |
| 当前状态 | 调查中、处置中、已止损、恢复中或已恢复 |
| 影响面 | 指标、用户/订单、资损、城市/渠道和数据来源 |
| 事故等级 | P0/P1/P2/P3 或“待定”，附定级依据/链接 |
| 时间线 | 发现、定位、开始止损、完全恢复及证据 |
| 通报对象与场景 | 事故群、管理层、业务方、客服/运营、舆情/G 侧等 |
| 通报人和下一节点 | 当前负责人、下次更新时间或复盘安排 |

缺少必填信息时只询问当前通报所需的最小字段；无法确认时生成带占位符的草稿并列出缺口。

## 执行流程

1. 先判断是首次通报、进展通报、恢复通报还是复盘前/管理层简报，并确认接收对象。
2. 建立事实表，标注来源为用户提供、监控取数、文档原文、推断或待确认。
3. 对照定级结果核验受影响业务方、事故发生时间、故障时长和完全恢复时间；故障时长仍按“核心指标开始下降至开始回升”口径。
4. 对 P0/P1 或潜在舆情/G 侧影响，列出需升级/同步的团队、负责人和时限；不把提醒写成已完成动作。
5. 生成对应场景的短通报，保证结论和当前状态在开头；最后列出下一更新时间和待补充项。
6. 输出发布前检查清单，等待用户确认后由用户自行发布。

## 输出模板

```markdown
## 事故通报草稿（<场景>）
**当前状态：** <调查中/处置中/已止损/恢复中/已恢复>
**事故等级：** <P0/P1/P2/P3/待定>（依据：<条款、指标、数据来源>）
**事故：** <名称/ID>
**受影响业务方：** <业务方/功能>
**事故发生时间：** <YYYY-MM-DD HH:mm Asia/Shanghai>
**故障时间：** <开始下降 ~ 开始回升；故障时长 X 分钟>
**完全恢复时间：** <时间或待确认>
**影响面：** <指标、比例、数量、范围、数据来源>
**已完成处置：** <动作与结果>
**正在进行：** <动作、负责人、预计完成时间>
**下一步/下次更新时间：** <内容和时间>
**通报人：** <姓名/团队>

### 待补充与升级提醒
- <缺失事实、证据链接、接收对象>
- <P0/P1、舆情或 G 侧需同步的团队与时限>
```

## 场景规则

- **事故群进展**：突出当前状态、影响、正在处置和下次更新时间，控制篇幅。
- **恢复通报**：明确开始止损与完全恢复的区别，附验证方式和遗留风险。
- **管理层简报**：增加等级依据、业务损失、责任/复盘计划，但不发布未经评审的责任结论。
- **舆情/G 侧**：按对应规范检查是否达到升级阈值；不代替专责团队判断或对外回应。

## 异常处理与安全

- 定级未完成时写“事故等级待定”，引导先使用「事故定级」skill，不擅自给等级。
- 影响数字、时间线或恢复状态冲突时保留各来源并标为待确认，不静默覆盖。
- 不自动发送、不伪造收件人、不在草稿中暴露无关敏感数据；外部发布需用户明确确认并遵循审批流程。
