# 事故复盘 Skill

## 触发条件

用户要求「复盘」「组织复盘会」「写复盘报告」「输出复盘文档」，或希望从已有复盘文档提取行动项时触发。

## 目标与边界

- 按《事后管理SOP》和《事故复盘模板》生成可评审、可追踪的复盘报告。
- 坚持不指责文化，复盘聚焦系统、流程、监控、测试和预案改进；责任判定交给「事故定责」skill。
- 原因未确认时标记「待定位」，给出补证计划，不凭空补齐根因。
- 输出改进项时必须同时具备负责人、截止日期和验证方式；缺项要单列待补充，并继续生成报告草稿。

## 必填输入（缺失时逐项收集）

### 事故信息

- 事故名称或事故 ID。
- 受影响业务方。
- 事故等级；未定级时先提示使用「事故定级」skill。
- 事故发生时间、开始止损时间、完全恢复时间；至少事故发生时间必须带日期和分钟。
- 故障现象、影响面和指标数据（可复用定级结果）。

### 分析与处置

- 直接原因、根因、为何引入、为何未在测试/监控/预案环节拦截。
- 处置时间线：时间、操作者/团队、动作、结果和证据链接。
- 参与方、沟通记录、决策依据和未解决风险。

### 改进项

每条改进项至少填写：具体行动、负责人（可定位到 DChat 个人）、截止日期、验证方式；建议增加改进项 ID、短期/长期类型、状态、关联链接。

## 名词口径

- **故障时长**：业务受损时刻（大盘指标开始下降）至业务开始恢复上涨时刻；不延伸到完全恢复时间。
- **完全恢复时间**：业务回到正常水平的时间，仅用于恢复耗时、不可用时长和时间线，不改变故障时长口径。

## 执行流程

1. 读取《事后管理SOP》和《事故复盘模板》正文；提取复盘时限、参会范围、章节结构和必填字段。抓取失败时停止套用未知模板，向用户索取正文或确认使用下方兜底结构。
2. 建立事实表：区分用户提供、监控取数、文档原文和待确认内容；统一时区和时间格式。
3. 复核时间线：事故发生 → 感知 → 定位 → 开始止损 → 完全恢复 → 验证恢复 → 复盘会/报告完成。
4. 按“五问法”或等价因果链分析直接原因、根因、触发条件、放大因素和拦截缺口；不把责任归属当作根因。
5. 检查监控、测试、变更、容量、预案、值班和沟通各环节，逐项写明“现状—缺口—证据—改进”。
6. 输出复盘报告草稿与结构化改进项表。改进项必须具体、可验收、可追踪；“加强监控”等宽泛表述改写为可执行动作，无法改写时标记待细化。
7. 报告完成后提示使用「改进项提醒」skill，按截止前 30/15/7/3/2/1 天和当天向负责人单独发送 DC 提醒。未经用户授权只生成待发送清单，不发送。

## 改进项质量检查

- 截止日期必须为具体日期，不能只写“尽快”“下周”。
- 负责人必须能映射到单个 DChat 用户；多人任务拆成多条或指定唯一 owner。
- 验证方式必须说明“完成后如何证明完成”，最好附链接、指标、测试用例或验收人。
- 已完成项保留完成时间和证据；未完成项必须有状态和下一步。
- 每条改进项应能由提醒 skill 直接解析，不把多个动作塞进一行。

## 异常处理

- 模板或 SOP 抓取失败：说明失败原因，请用户提供原文；在用户确认前不声称“严格按模板”。
- 时间、指标或原因缺失：报告中保留“待确认/待定位”，不编造。
- 改进项缺负责人或日期：照常输出报告，但列入“待补充”，不发送 DC 提醒。
- 复盘文档中没有改进项：明确提示“当前无可提醒任务”，不生成虚假任务。
