# 改进项提醒 Skill

## 触发条件

用户要求「提醒改进项」「检查复盘改进项」「催办复盘任务」「发送改进项到期提醒」，或复盘报告中出现带负责人和截止日期的改进项时触发。

本 skill 负责从复盘文档提取、校验、计算和发送改进项提醒；不修改复盘文档内容，不替负责人完成任务，不代替事故定责。

## 输入

### 必填输入

- 复盘文档正文或可读取的复盘文档链接。
- 事故标识：事故名称或事故 ID，至少一个可稳定识别事故的字段。
- 执行日期和时区：由顶层 harness 注入 `execution_date` 和 `Asia/Shanghai`；用户指定日期时以用户指定为准，不能由模型自行读取当前日期。

### 改进项必填字段

复盘文档中的每条改进项至少应能解析出：

| 字段 | 说明 |
|---|---|
| 改进项 | 具体、可验收的行动，不接受只有“持续关注”或“加强意识”这类不可执行描述 |
| 负责人 | DChat 可定位的个人 LDAP 用户名或 user_id；“某团队”不能直接作为私聊收件人 |
| 截止日期 | `YYYY-MM-DD` 或可无歧义解析的日期；带时间时按 `Asia/Shanghai` 处理 |
| 验证方式 | 验收标准、链接、产物或验证人；缺失时标为待补充，不阻断提醒 |

可选字段：改进项 ID、短期/长期类型、所属团队、当前状态、完成时间、关联链接、备注。

## 提取与校验

1. 优先读取复盘文档中的「改进项/后续行动/Action Items」表格；没有表格时再解析结构化列表。
2. 支持中文表头别名：
   - 改进项：`改进项`、`行动项`、`问题改进`、`Action Item`、`Task`
   - 负责人：`负责人`、`Owner`、`Assignee`
   - 截止日期：`截止时间`、`完成时间`、`DDL`、`Due Date`
   - 验证方式：`验证方式`、`验收标准`、`验收方式`、`验证标准`
3. 日期只解析为日历日期；禁止把“30天内”或“尽快”猜成具体日期。无法解析时列入待补充清单，不发送该条提醒。
4. 负责人优先使用文档中明确的 LDAP 用户名或 user_id。中文姓名、昵称或团队名无法唯一映射时，先请求用户补充映射，不向错误对象发送。
5. 状态为已完成、已关闭、已取消、无需执行的改进项不发送提醒；状态缺失视为未完成，但在结果中标注“状态待确认”。
6. 同一事故下相同改进项、负责人、截止日期视为同一任务；保留原文链接和行号/段落位置用于追溯。

## 提醒触发规则

### 触发日

按“截止日期 − manifest.execution_date”的自然日差计算，两个日期都按 `Asia/Shanghai` 的本地日期比较。仅在以下 7 个节点发送：

| 节点 | 条件 | 消息级别 |
|---:|---|---|
| 30 天 | 距截止日期 30 天 | 提前提醒 |
| 15 天 | 距截止日期 15 天 | 提前提醒 |
| 7 天 | 距截止日期 7 天 | 重点提醒 |
| 3 天 | 距截止日期 3 天 | 紧急提醒 |
| 2 天 | 距截止日期 2 天 | 紧急提醒 |
| 1 天 | 距截止日期 1 天 | 紧急提醒 |
| 当天 | 距截止日期 0 天 | 到期提醒 |

“截止日期 30 天内”表示 `0 <= 距截止日期 <= 30` 的改进项；但实际发送只发生在上述节点。逾期任务（差值小于 0）不套用历史节点，发送一条“已逾期”提醒仅在用户明确要求检查逾期项时触发。

## 幂等与调度

- 提醒唯一键：`事故ID/事故名称 + 改进项ID（无则用规范化改进项文本） + 负责人 + 截止日期 + 节点`。
- 同一唯一键已成功发送时不得重复发送；重试只针对失败记录。
- 运行方式可为定时任务或用户手动触发。若当前环境没有可用调度器，必须明确告知用户无法自动唤醒，并输出可直接配置的调度规则及待发送清单，不得声称已完成自动发送。
- 调度至少每日执行一次，建议在 `09:00 Asia/Shanghai` 执行；执行器把本次检查日期写入 manifest，实际发送日期由自然日差决定。
- 发送前重新读取文档或状态源，避免已完成任务继续提醒。

## DChat 单独提醒

1. 每条改进项按负责人分别发送一条 DChat 私聊消息；禁止把多个负责人的任务合并到群消息，也禁止仅 @ 用户代替私聊。
2. 使用 DChat 消息发送能力（`message:write`），优先发送 `markdown`，不支持时降级为 `text`。收件人使用 `username` 或 `user_id`，二选一。
3. 消息必须包含：提醒节点、事故名称/ID、改进项原文、截止日期、剩余天数或逾期天数、验证方式、复盘文档链接、回复/更新状态的方式。
4. 按 DChat `POST /v1/message.create` 的约定组装请求：单个收件人、`msg_type`（`markdown` 或 `text`）和消息正文；收件人不得同时填入群聊标识或多个用户。请求中的事故/任务幂等键与本 skill 的唯一键保持一致，便于重试和审计。
5. 只有接口返回成功码且服务端确认消息已接收，才将结果记为“已发送”；超时、鉴权失败、会话未建立、参数错误和非成功码均记为“发送失败”，保留错误码和重试建议。
6. 推荐消息模板：

```markdown
【复盘改进项提醒｜距截止 7 天】
事故：<事故名称>（<事故ID>）
改进项：<改进项>
截止日期：<YYYY-MM-DD>
剩余时间：7 天
负责人：<用户名>
验证方式：<验证方式>
复盘文档：<链接>
请在完成后更新状态并补充验证证据；如需调整截止日期，请先反馈新的日期和原因。
```

7. 单条消息建议不超过 4096 字符；长链接保留原链接，不伪造短链。
8. 发送前检查 DChat 认证环境、`message:write` 权限及 Bot 与用户是否已建立会话。认证缺失、用户不可解析、接口返回非成功码时，记录失败原因并输出人工处理清单，不重复盲目重试。
9. 结果中逐条列明：已发送、已跳过（原因）、待补充、发送失败（错误码/原因）。不得把“已生成消息”描述成“已发送”。

## 输出格式

```markdown
## 改进项提醒结果

**检查日期**：2026-09-22（Asia/Shanghai）
**事故**：<事故名称/ID>
**本次应提醒**：<数量> 条
**已发送**：<数量> 条
**已跳过**：<数量> 条
**待补充**：<数量> 条
**发送失败**：<数量> 条

### 发送明细
| 负责人 | 改进项 | 截止日期 | 节点 | 结果 | 备注 |
|---|---|---:|---:|---|---|

### 待补充/异常
- <缺少负责人、日期、用户映射、文档权限或 DChat 权限等>
```

## 边界与安全要求

- 不向群聊、非负责人或无法确认身份的对象发送。
- 不泄露事故不必要的敏感信息；消息只包含该负责人需要执行的改进项。
- 复盘文档读取失败时停止发送，先报告权限/链接问题。
- 截止日期变更后，以最新文档为准；旧节点的成功记录不删除，新节点按新日期重新计算。
- 发送动作属于外部写操作，除非用户已明确授权自动提醒，否则先展示待发送清单并请求确认。
